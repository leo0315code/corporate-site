## 一、产品目标与背景

### 1.1 一句话

为后台增加一个**只读、可信、不可篡改的操作审计流水**：把「谁、在什么时间、对哪个对象、做了什么、结果如何、从哪个 IP 来」全部落库，并提供后台查询页，让追责与排查有据可查。

### 1.2 真实缺口（为什么现在做）

账号管理（C-P1-4，见 `PRD-CMS.md` §5.6 / §7.8）交付后，系统已有**多个权限完全相同的管理员账号**，但：

1. **任何管理员对任何内容/账号的操作，全程没有任何记录可查**。数据库里只有「当前状态」（内容是什么、账号是启用还是停用），没有「变更历史」与「操作者」。
2. **存在真实的接管风险**：若 A、B 两个管理员互相知晓密码（或 A 的密码被 B 看到），B 可以直接把 A 的账号**停用 / 删除**，然后以自己身份继续操作，无人能审计、无人能发现。
3. **停用/删除是「静默」的**：被停用的账号只会发现自己登录不上，运营主管无法回答「谁停用的、什么时候停用的、为什么」。
4. **内容误删/误改无法回溯**：`CMS-USAGE.md` §7.12 已明确「删除内容记录不联动删除图片」，但连「谁删的这条记录」都没有记录，只能靠猜。
5. **登录安全事件缺少上下文**：`PRD-CMS.md` §6.2 有「失败 5 次锁定」，但锁定记录只用于计数与解锁，**不保留历史**；安全事件回溯时看不到「哪些账号/IP 在什么时段被反复尝试」。

**结论**：这不是「缺超级管理员」的问题，而是**缺审计**的问题。再细化权限（RBAC）之前，必须先把「可追溯」补上——**操作日志是 RBAC（C-P2-2）的天然前置**：没有日志，任何权限模型都无法验证其是否被正确执行。

### 1.3 明确不做（与「补权限」划清界限）

- 本期**不做角色/权限区分**（RBAC 仍列 C-P2-2，见 `PRD-CMS.md` §4 P2）。
- 本期**不做「日志阻断操作」**：日志是旁路记录，**不参与**业务放行判定（不能因「写日志失败」而拒绝一次合法的内容保存）。
- 本期**不做日志的对外 API**：日志仅通过后台查询页读取，**不提供匿名接口**。
- 本期**只读**：不提供「删除日志」「编辑日志」入口（清理机制见第八节，且不由 UI 触发）。

### 1.4 三个产品目标（正交）

| # | 目标 | 可度量判据 |
| --- | --- | --- |
| G1 | **可追溯**：任何一次写操作都能回答「谁、何时、对谁、做了什么」 | 第 5.2 节「要记」清单中的每类操作，**100%** 在库中留有至少 1 条日志 |
| G2 | **可排查**：运营主管能在 1 分钟内定位「某条内容/某个账号最近发生了什么」 | 支持按模块 + 对象 + 时间范围 + 操作人 + 关键词组合筛选，命中结果可下钻详情 |
| G3 | **不泄密**：日志本身不成为新的安全风险 | 日志中**绝不**出现明文密码、密码哈希、Token（见第九节），且日志接口受与其它管理接口同级的鉴权保护 |

## 二、增量用户故事

> 角色统一为**运营主管**（比「运营人员」更高一层，关注全局与追责）；第 5 条的安全事件回溯涉及**安全/技术负责人**。

1. **作为运营主管**，我希望在后台看到「谁在什么时候改了什么内容」，以便确认网站上的改动都是被授权的。
2. **作为运营主管**，我希望在内容被误删或误改后能查到这个页面**曾经被谁动过**，以便定位责任人并决定是否需要恢复。
3. **作为运营主管**，我希望追溯**某个账号为什么被停用/删除、是谁操作的**，以便在员工离职交接或纠纷时给出确切依据（而不是只能看到「账号现在是停用的」）。
4. **作为运营主管**，我希望按**操作人、模块、时间范围**筛选日志，以便快速缩小范围（例如「上周是谁动了新闻模块」）。
5. **作为安全/技术负责人**，我希望看到**登录成功与失败的历史（含 IP、UA、结果）**，以便在一次疑似爆破后回溯「哪些 IP 在什么时段被反复尝试、是否有账号被锁定」。
6. **作为运营主管**，我希望日志页**只能看、不能改、不能删**，以便这份记录在争议时是可采信的。

## 四、日志字段定义

> **设计原则**：字段**够用于追责与排查**，不多记。`detail` 为可扩展字段，用于承载「变化摘要」等模块特有信息。

| # | 字段名 | 类型 | 必填 | 说明 | 示例值 | 设计理由 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | `id` | int UNSIGNED 自增 | 是（系统） | 日志主键 | `1024` | 唯一标识，详情页按此查；自增便于按时间顺序自然排列 |
| 2 | `admin_id` | int | 否 | 操作人 ID；**登录失败时可为 0**（账号可能不存在） | `2` | 关联 `admin_user.id`，用于按操作人筛选；为 0 表示「未识别到有效账号」 |
| 3 | `admin_name` | varchar(50) | 是 | 操作人账号名**快照** | `ops-a` | **关键**：账号可能被改名或删除，日志必须自带不可变的账号名快照，否则事后无法还原「当时操作的人叫什么」 |
| 4 | `created_at` | datetime | 是 | 操作时间（服务端时间，秒级） | `2026-02-14 10:22:31` | 追责的第一要素；由服务端生成，**不接受前端传入**（防伪造） |
| 5 | `module` | varchar(20) | 是 | 业务模块标识（枚举见 §4.2） | `news` | 按模块筛选与聚合；用稳定英文标识而非中文名，便于后续机器处理 |
| 6 | `action` | varchar(20) | 是 | 动作标识（枚举见 §4.3） | `update` | 区分「做了什么」，是筛选与阅读的核心维度 |
| 7 | `target` | varchar(120) | 否 | 目标对象**可读标识** | `news-2025-06` / `ops-b` | 回答「对谁做的」；内容模块填业务 id（slug），账号模块填账号名，站点配置填 `site_config` |
| 8 | `target_name` | varchar(120) | 否 | 目标对象**人类可读名称**（辅助） | `2025 年中产品发布会` | 让非技术人员看得懂；内容被删除后仍能知道「当时删的是什么」 |
| 9 | `ip` | varchar(45) | 是 | 来源 IP（兼容 IPv6） | `203.0.113.24` | 定位来源；与登录锁定维度（见 PRD-CMS.md §6.2）对齐，便于关联安全事件 |
| 10 | `user_agent` | varchar(255) | 否 | 请求 UA，截断 255 | `Mozilla/5.0 (Windows …)` | 区分「同一账号在不同设备操作」；截断防超长 |
| 11 | `result` | tinyint | 是 | 执行结果：`1`=成功，`0`=失败 | `1` | 成功与失败都必须留痕；失败日志是排查「为什么没生效」的关键 |
| 12 | `detail` | varchar(500) / JSON 文本 | 否 | 变化摘要 / 失败原因（见 §4.4） | `+3 字段, -1 字段` / `账号或密码错误` | 承载模块特有信息，兼顾「人可读」与「可扩展」；**长度受限**以控制存储膨胀 |

### 4.1 字段取舍说明

- **为什么记 `admin_name` 快照而不只记 `admin_id`**：账号可被改名（当前系统虽无改名入口，但删除后 id 可能被复用语义混淆），且**删除账号后 `admin_id` 指向的行不存在**。快照保证日志**自解释**，无需联表即可阅读——这是审计日志的基本要求。
- **为什么 `ip` 必填而 `user_agent` 选填**：IP 是安全回溯的硬性依据；UA 缺失（如脚本请求）不应导致日志写入失败。
- **为什么 `result` 用 `tinyint` 而非字符串**：与全站既有风格一致（`status` / `is_primary` 均用 number），前端渲染为「成功/失败」标签。
- **为什么 `detail` 限制 500 字符**：日志表是**高增长表**，必须控制单行体积；超出部分截断并追加 `…`，完整内容不在本期诉求内（完整 diff 见 C-P1-3.8）。

| 上传 | 落盘路径 + 字节数 + MIME | `/uploads/news/ab12….png, 128KB, image/png` |

## 五、记录范围界定

### 5.1 判定原则

> **记「状态被改变」的操作；不记「状态未改变」的读取。**
> 理由：日志的价值是「回答发生了什么变更」。纯读取（列表/详情）不改变任何状态，记录它只会让日志量随运营强度**线性膨胀**（例如每次翻页、每次搜索都落库），把真正需要关注的变更**淹没**在噪声里，反而降低可排查性（违反 G2）。同时日志表是**追加写**的高增长表，控制写入量直接关系到性能与留存成本（见第八节）。

### 5.2 要记（本期 P0 清单，务必逐条对齐）

| # | 操作 | 触发点（已有接口） | `module` | `action` | 是否记 `result=0` |
| --- | --- | --- | --- | --- | --- |
| 1 | 登录成功 | `{P}/api/login` | `auth` | `login` | 否（成功即 1） |
| 2 | **登录失败** | `{P}/api/login` | `auth` | `login` | **是**（含锁定失败也记） |
| 3 | 登出 | `{P}/api/logout` | `auth` | `logout` | 否 |
| 4 | 内容增/删/改（产品） | `content/product/{save,delete}` | `product` | `create`/`update`/`delete` | 是（校验失败/重复 id 记 `result=0`） |
| 5 | 内容增/删/改（新闻） | `content/news/{save,delete}` | `news` | 同上 | 是 |
| 6 | 内容增/删/改（案例） | `content/case/{save,delete}` | `case` | 同上 | 是 |
| 7 | 内容增/删/改（优势） | `content/advantage/{save,delete}` | `advantage` | 同上 | 是 |
| 8 | 关于我们整页保存 | `content/about/save` | `about` | `update` | 是 |
| 9 | **网站配置保存** | `content/site/save` | `site` | `update` | 是 |
| 10 | 留言标记状态 | `message/status` | `message` | `update` | 是 |
| 11 | 留言删除 | `message/delete` | `message` | `delete` | 是 |
| 12 | 账号新建 | `admin/create` | `account` | `create` | 是（重名 `1002` 也记） |
| 13 | 账号启用 / 停用 | `admin/toggle-status` | `account` | `enable`/`disable` | 是（保底约束拒绝也记） |
| 14 | 账号重置密码 | `admin/reset-password` | `account` | `reset_password` | 是 |
| 15 | 账号删除 | `admin/delete` | `account` | `delete` | 是（二次确认不匹配也记 `result=0`） |
| 16 | 图片上传 | `upload/image` | `upload` | `upload` | 是（格式/大小拒绝也记） |
| 17 | 本人改密（常规） | `auth/password` | `auth` | `change_password` | 是（原密码错误记 `result=0`） |
| 18 | 首次强制改密 | `auth/reset-password` | `auth` | `change_password` | 是 |

> **`result=0`（失败）也要记的理由**：失败日志是排查的两大关键场景之一——(a) 安全回溯：谁在反复尝试登录、在哪个 IP；(b) 运营求助：用户说「我明明保存了」，日志能立刻回答「这次保存是否真的到达后端、后端拒绝了什么」。只记成功会让这两类问题重新变成盲区。

### 5.3 不记，但给出我的判断（**建议主理人确认**）

| # | 操作 | 我的判断 | 理由 |
| --- | --- | --- | --- |
| 1 | 内容列表查询 / 详情查询（内容 5 类的 `list`/`detail`） | **不记** | 不改变状态；运营每次翻页/搜索都记 → 日志量级放大数十倍，噪声淹没信号 |
| 2 | 留言列表 / 留言详情 | **不记** | 同上。留言**内容本身**含客户隐私，记录「某人查看过某条留言」收益低、且日志会二次留存隐私 |
| 3 | 账号列表查询 | **不记** | 同上 |
| 4 | 日志页自身的查询 | **不记** | 若记，会形成「看日志产生新日志」的自指膨胀 |
| 5 | `auth/profile`（取当前登录者资料） | **不记** | 高频、无状态改变、无审计价值 |
| 6 | 上传图片的**二进制内容** | **不记** | 只记路径与元信息；存内容既无必要又造成存储与合规风险 |
| 7 | 失败请求中的**请求体原文** | **不记** | 请求体可能含密码等敏感信息（见第九节）；只记「失败原因」这一结构化结论 |

> **我唯一犹豫并倾向于「可记」的例外**：**留言详情的查看**（上表第 2 条）。若主理人认为客户线索属于敏感数据、需要「谁看过客户的联系方式」的追溯，可把留言详情查看**单列 P1**（`module=message, action=view_detail, target=<留言 id>`）。因留言查看频次远低于内容列表翻页，噪声可控。**默认本期不做**，请主理人在 §10 拍板。

## 六、后台日志查询页 UI 设计

### 6.1 页面在信息架构中的位置

## 七、与已有模块的边界（引用，不重复）

- **鉴权**：日志页与日志查询接口**必须**挂在 `AdminAuth` 中间件之内（见 `PRD-CMS.md` §6.6 越权防护）；未登录/Token 失效返回 `1003`。
- **强制改密闸门**：日志接口**不在** `AdminAuth::$pwdWhitelist` 内，未改初始密码的账号访问日志页同样返回 `1006`（与账号管理一致，见 `PRD-CMS.md` §5.6）。
- **响应结构**：日志接口沿用全站 `{code, message, data}`（见 `backend/app/common.php`）。
- **错误码**：本期**不新增错误码**，复用 `1001/1003/4004/5000`（见 `PRD-CMS.md` §6.7）。查询参数非法 → `1001`；日志 id 不存在 → `4004`。
- **内容缓存**：日志页为纯后台读，**不挂** `ContentCache`（该中间件用于前台公共内容 GET）。
- **账号删除后的日志可读性**：账号被硬删后，其历史日志**不级联删除**（否则等于删除证据），仍可按 `admin_name` 快照阅读与筛选。

## 八、保留策略

### 8.1 结论

| 项 | 决策 | 理由 |
| --- | --- | --- |
| 默认保留期 | **180 天（约 6 个月）** | 平衡「审计可用」与「存储可控」；覆盖绝大多数追责窗口（离职交接、季度复盘、纠纷时效） |
| 清理机制 | **提供**（后端命令行清理命令），**但不做 UI 触发** | 避免「有权限的人删掉对自己不利的日志」；清理只能由运维在服务器侧执行 |
| 本期是否实现自动清理 | **不实现定时任务**；只提供**幂等、可手动执行的清理命令** | 项目当前无任务调度基础设施（`PRD-CMS.md` §12 明确不引入额外框架），引入 cron/队列属范围蔓延 |
| 是否可配置保留天数 | **是**，通过环境变量配置（默认 180） | 不同企业合规要求不同，避免硬编码 |
| 单次清理上限 | 提供 `--limit` 参数（默认一次最多删 N 条），避免一次性大删锁表 | 保护线上库 |
| 是否做归档 | **不做** | 归档到冷存储涉及存储与恢复流程，超出本期范围 |

### 8.2 设计要求

1. 清理按 `created_at < now - 保留天数` 分批删除（默认每批上限如 5000 条，可循环执行至清完）。
2. 清理动作**本身不写日志**（否则自指膨胀）；但**必须打印清理条数**到终端，便于运维留痕。
3. 日志表**只增不改**：本期**不提供**任何 UPDATE 日志的接口或 SQL 路径（审计日志的完整性要求）。
4. **落地建议（供架构师评估）**：`created_at` 上建索引（`idx_created`），模块/操作人/结果按需建组合索引；具体索引方案由架构师定（见 §10 Q4）。

### 8.3 为什么不在本期做自动清理

引入定时任务需新增调度设施，与「不引入第三方依赖」「不做框架外机制」的约束冲突；且日志量在中小站点可预期间（按日均数百条估算，180 天约数万至十几万行，MySQL 完全可承受）。**先保证「记全」与「能查」，再按实际量级决定是否上调度。**

## 九、与安全的边界（**绝不能**出现在日志中的内容）

> 这是本期**红线**，架构师与工程师都必须逐条落实。

| # | 禁止项 | 具体说明 | 落地要求 |
| --- | --- | --- | --- |
| 1 | **明文密码** | 登录密码、新密码、确认密码、旧密码 | 日志写入器**不接受**任何密码字段；登录日志只记 `result` 与**结构化失败原因**，不记请求体 |
| 2 | **密码哈希** | bcrypt 哈希串（`$2y$…`） | 与 `PRD-CMS.md` §6.1 / §7.8 一致：任何接口/日志**不返回、不落日志** |
| 3 | **会话 Token** | `Authorization: Bearer <token>` 中的 token | 日志**不记**请求头；`PRD-CMS.md` §6.6 已明确「Token 不得出现在 URL/日志」，本期延续 |
| 4 | **完整请求体原文** | 尤其 `admin/create`、`auth/*` 的 body | 只记**白名单抽取后的结构化字段**（如账号名、目标 id），不 dump 原 body |
| 5 | **重置密码产生的一次性随机密码** | 见 `PRD-CMS.md` §5.6 | 日志只记「重置了谁」+「一次性密码未记录」，**绝不落明文** |
| 6 | **登录失败的原因区分** | 不得写成「账号不存在」/「密码错误」 | 与 `PRD-CMS.md` §5.1「防枚举」一致，日志统一为「账号或密码错误」，避免日志成为账号枚举渠道 |
| 7 | **数据库/堆栈细节** | 异常信息 | 失败原因只记**业务层可读文案**，不记 SQL、表名、堆栈（对齐 §6.6 敏感信息要求） |
| 8 | **拦截码/敏感凭证** | 如未来接入的密钥 | 本期无此场景，但写入器应实现**字段白名单**（只允许 §4 定义的字段），从机制上防止未来误加敏感字段 |

**额外安全要求**：

- **日志查询接口的越权边界**：日志可能暴露「账号名、IP、操作轨迹」，属**内部治理数据**。当前所有管理员权限相同（无 RBAC，见 `PRD-CMS.md` §5.6），因此**所有管理员都可查看全部日志**——这是本期可接受的（因为管理员本就权限相同）。**待 RBAC（C-P2-2）落地后**，应将「查看日志」收敛为受限权限（见 §10 Q6）。
- **只读保证**：后端日志模块**只提供读接口**（`list` / `detail`），不提供写/删接口；日志写入是**服务内部调用**，不经 HTTP。
- **写入旁路**：写日志失败**不得**导致主业务失败（try/catch 包裹），但**必须**记录一条错误到框架日志，避免「静默丢日志」无人知晓。

## 十一、验收标准（增量）

| 项 | 标准 |
| --- | --- |
| 记录完整性 | §5.2 清单的 **18 类操作**逐一验证：执行后库中均有对应日志，且 `module/action/target/result` 正确 |
| 失败留痕 | 登录失败、内容保存校验失败、账号删除二次确认不匹配、上传格式拒绝，均产生 `result=0` 日志并含失败原因 |
| 字段完整性 | 每条日志 `admin_name / created_at / module / action / ip / result` 非空；`created_at` 为服务端时间 |
| 登录失败原因不泄露 | 日志中登录失败原因为统一文案，**不含**「账号不存在」等可枚举信息 |
| 账号名快照 | 删除某账号后，其历史日志仍显示原账号名，且可按该账号名筛选出全部记录 |
| 敏感信息零泄露 | **全表扫描**确认：无明文密码、无 bcrypt 哈希串、无 Token；重置密码日志不含随机密码 |
| 查询页可用 | 可按模块/操作人/时间范围/关键词/结果筛选 + 分页 + 查看详情；默认最近 7 天 |
| 导航位置 | 「操作日志」位于「账号管理」与「修改密码」之间；`CmsLayout` 页面标题正确显示 |
| 只读保证 | 后台日志页**无**删除/编辑入口；后端**无**日志写/删 HTTP 接口 |
| 鉴权 | 未带 Token 访问日志接口返回 `1003`；未改初始密码访问返回 `1006` |
| 不阻断业务 | 人为使日志写入异常时，内容保存/账号管理主流程**仍成功**，且框架日志中有错误记录 |
| 保留策略 | 清理命令按保留天数与 `--limit` 分批删除，幂等可重跑，打印删除条数；DB 中 `created_at` 有索引 |
| 响应式 | 375px 下表格可横向滚动、无横向溢出；筛选区可正常操作 |
| 一致性 | 日志接口响应统一 `{code,message,data}`；不新增错误码 |
