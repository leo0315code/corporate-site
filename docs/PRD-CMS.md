## 一、变更概述

**一句话**：把目前写死在前端 TS 文件里的全部网站内容（产品 / 新闻 / 案例 / 优势 / 关于我们 / 网站配置）迁移到 MySQL，并新增一个**路径可配置、带真实安全防护的 CMS 后台**，让企业运营人员无需改代码、无需重新构建即可在线增删改内容，前台通过 API 动态读取、即时生效。

**本次增量的三个核心动作**：

1. **内容上云**：5 类内容从 `frontend/src/data/*.ts`（约 373 行）迁入数据库，**另将 `frontend/src/config/site.config.ts` 的站点基础信息（公司信息/联系方式/页脚/SEO）作为「网站配置」单例上云（静态文件保留为兜底值）**，并提供初始化导入脚本把现有示例内容无损导入。
2. **新增后台（CMS）**：登录 + 5 类内容 CRUD + 网站配置编辑 + 留言查看与管理 + 修改密码/登出。
3. **前台改造**：把「静态 import 数据文件」改为「API 动态读取」，后台改完刷新即生效。

**为什么做**：原 PRD 把「内容配置化」落地为「改 TS 文件 + 重新构建部署」，对**非技术运营人员不可用**；原 PRD Q7/A6 也把后台列为「默认不做」。用户现已明确要求补齐这一块（原需求原文：「肯定都需要改啊 产品 新闻 啥的都是写死的」）。

**用户已拍板的 4 项决策（不可更改）**：

| 决策项 | 用户选择 |
| --- | --- |
| 管理范围 | **全部内容**：产品、新闻、案例、优势、关于我们 全部可在线增删改 |
| 前台取数方式 | **API 动态读取**（后台改完即时生效，无需重新构建） |
| 后台入口形式 | **可配置路径前缀**（写在环境变量，前后台同域部署） |
| 安全强度 | **标准安全**：bcrypt 密码哈希 + 登录失败锁定（5 次锁 10 分钟）+ 会话 Token 过期 + 首次登录强制改密 + 无默认弱密码 |

## 二、现状痛点

内容写死在前端 TS 文件带来的实际问题，逐条如下：

1. **运营无法自助改内容**：产品/新闻等全部写死在 `frontend/src/data/products.ts`、`news.ts`、`about.ts`、`advantages.ts`、`cases.ts` 中，改一句话都要开发介入，运营完全被动。
2. **改内容必须重新构建 + 重新部署**：任何内容变更都要改源码 → `npm run build` → 替换静态产物，链路长、有出错风险，且需要开发/运维权限。
3. **没有回滚与留痕**：没有历史版本、没有操作记录，改错了只能靠 git 回退源码。
4. **内容无法搜索、分页、筛选**：数据在内存数组里，量一多（如新闻上百条）无法在后台高效检索。
5. **留言只能进库、看不到**：`POST /api/message` 已能入库，但后台不可见（原 PRD 仅留了 `GET /api/message/list` 接口，无界面、无鉴权），线索无法被跟进处理。
6. **无认证体系**：现有系统没有任何登录/权限概念，微信式裸露接口 `GET /api/message/list` 会泄露客户线索。
7. **前后端耦合导致通用性受损**：原 PRD 追求「换企业只改配置」，但改配置仍是改代码，与「通用、可复用」目标存在落差。
8. **上线效率低**：每次内容微调都要走一次完整发版流程，违背「便捷操作」的原始诉求。

## 三、增量用户故事

> 均为**新增**用户故事（原 PRD 第 4 节的 6 条访客/运营故事仍有效）。角色统一为「企业运营人员」。

1. **作为企业运营人员**，我希望用账号密码安全登录后台，以便只有授权的人才能管理网站内容。
2. **作为企业运营人员**，我希望首次登录时被强制修改初始密码，以便避免使用系统下发的初始弱口令带来的安全风险。
3. **作为企业运营人员**，我希望在后台对产品/服务进行新增、编辑、删除、搜索，以便随时更新对外的产品与服务介绍。
4. **作为企业运营人员**，我希望在后台管理新闻（含标题、日期、分类、封面、摘要、正文），以便及时发布公司动态与行业资讯。
5. **作为企业运营人员**，我希望在后台管理客户案例（名称、Logo、描述），以便展示最新的合作成果。
6. **作为企业运营人员**，我希望在后台管理首页「数据与优势」指标（数值、标题、说明），以便让首页的关键数字始终真实准确。
7. **作为企业运营人员**，我希望在后台编辑「关于我们」的简介、愿景、使命、价值观、发展历程与能力资质，以便公司介绍与最新情况保持一致。
8. **作为企业运营人员**，我希望在后台查看并管理访客留言（列表、详情、关键词搜索、标记处理状态、删除），以便及时跟进销售线索。
9. **作为企业运营人员**，我希望随时修改自己的登录密码，以便账号安全可控。
10. **作为企业运营人员**，我希望在不用电脑时能一键安全登出，以便会话不被他人盗用。
11. **作为企业运营人员**，我希望后台地址不是默认的 `/admin` 而是可自定义的路径，以便降低被批量扫描爆破的风险。
12. **作为访客/潜在客户**，我希望官网内容始终是最新且加载顺畅的，以便我看到的公司信息是准确、可信的。

### 5.1 登录页 `/{CMS_PATH}/login`

| 区域 | 内容 | 交互 |

### 5.2 内容管理模块通用结构（产品 / 新闻 / 案例 / 优势）

### 5.5 修改密码页 `/{CMS_PATH}/password`

> **位置**：位于后台外壳（`CmsLayout` 侧栏 + 顶栏）**之内**，与其它管理页一致；运营改密后可随时经侧栏返回其它模块。入口：侧栏导航「修改密码」+ 顶栏「修改密码」按钮。

| 字段 | 规则 |
| --- | --- |
| 原密码 | 必填，需与当前密码一致 |
| 新密码 | 必填，长度 ≥ 8，含大小写字母 + 数字（建议），不得与原密码相同 |
| 确认新密码 | 必填，需与新密码一致 |

成功 → Toast「密码修改成功」+ 强制重新登录（旧 Token 失效）。

### 5.6 账号管理页 `/{CMS_PATH}/accounts`

> **定位**：本页是 C-P1-4「多管理员账号」（⚑ 已提前交付）的落地面。多个后台账号**权限完全相同**，仅用于「一人一账号」以便追溯与个人改密；**不做角色/权限区分**（RBAC 仍列 C-P2-2）。

| 功能区 | 说明 |
| --- | --- |
| 列表 | 表格：ID、账号（标注「主账号」/「当前登录」）、状态（启用/停用）、密码状态（正常/待改密）、最近登录时间、最近登录 IP、创建时间、操作 |
| 搜索 | 按账号名关键词搜索 + 分页 |
| 新建账号 | 右上角「新建账号」→ 输入账号名（字母开头，3–50 位，可含字母/数字/`_`/`-`）→ 系统**自动生成一次性随机强密码**并弹窗展示 |
| 一次性密码展示 | 新建成功后弹「凭据面板」展示账号名 + 随机强密码，提供**复制**按钮，并明确提示「**仅本次展示**」；关闭后不再可见 |
| 启用 / 停用 | 行内按钮切换状态。**停用（软删）为默认推荐操作**，可逆；停用后该账号的会话**立即全部失效**（被踢下线） |
| 重置密码 | 行内「重置密码」→ 二次确认 → 系统重新生成一次性随机强密码 → 凭据面板展示，且该账号被标记「待改密」并**立即踢下线** |
| 删除（硬删） | 行内「删除」→ 二次确认弹窗中**要求手动输入该账号名**再次确认 → 才执行物理删除 |
| 自锁保护 | **当前登录账号**不可停用、不可重置自身密码、不可删除（对应按钮置灰并给出提示） |
| 主账号保护 | **主账号**（`cms:init` 创建的初始管理员，`is_primary = 1`）不可停用、不可删除（按钮置灰并提示原因）；但仍可被**启用**、可被重置密码 |
| 保底约束 | 停用/删除一个**启用中**的账号时，必须保证全站**至少保留 1 个启用账号**，否则拒绝 |

**安全约束（后端强制，前端同步禁用）**：

1. **不能停用/删除当前登录账号**——避免把自己锁在后台之外。
2. **不能重置自己的密码**——重置会生成一次性随机密码且强制改密；若作用于自己，改密前的旧密码与新建时的一次性密码都将无效，导致无法登录。
3. **至少保留 1 个启用账号**——停用/删除需在事务内加行锁校验，保证并发下也不会把启用账号清零。
4. **账号名不可重复**——包含已停用的账号；新建重复账号返回 `code=1002`。
5. **响应绝不返回密码哈希**——密码仅以明文一次性返回给发起创建的当前登录账号，落库只存 bcrypt 哈希。
6. **主账号不可停用 / 不可删除**——主账号是 `cms:init` 创建的**初始入口账号**，用于防止「新建账号后把初始账号误删 / 恶意停用后接管」。该标记**不带来额外权限**（管理员之间权限仍完全等同），仅作护栏；后台**不提供**转移主账号的入口（如需更换，走 CLI / 数据库操作）。

> **主账号的产生与回填**：`cms:init` 首次创建管理员时直接标记 `is_primary = 1`；老库升级时若库中尚无主账号，建表脚本会把**最早创建**的管理员（`id` 最小）回填为主账号，保证「任一时刻恰好有 1 个主账号」。

## 六、安全需求（重点）

> 用户选择「标准安全」，以下为**逐条明确**的硬性要求，均为 P0。

### 6.1 密码存储

- 使用 PHP 内置 `password_hash($pwd, PASSWORD_BCRYPT)` 存储，**禁止明文/MD5/SHA1**。
- 校验用 `password_verify()`；哈希与校验必须走框架封装，禁止自定义加密。
- 数据库仅存哈希串，任何接口/日志/响应**不得返回密码或哈希**。

### 6.2 登录失败锁定

- 连续登录失败 **5 次**，锁定 **10 分钟**。
- 锁定维度：**账号 + IP 双维度**（同一账号在多 IP 被爆破 → 锁定账号；同一 IP 尝试多个账号 → 锁定 IP）。
- 锁定期内即使密码正确也拒绝，提示「登录失败次数过多，请 X 分钟后再试」。
- 登录成功后清零该账号/该 IP 的失败计数。
- 失败计数与锁定时间持久化（存数据库，避免重启/多进程失效）。

### 6.3 会话（Token）机制

- 登录成功后后端签发 Token（随机强随机串），**服务端保存 Token 及其有效期**。
- Token 有效期建议 **2 小时**；过期后所有管理 API 返回「未授权」，前端自动跳登录页。
- 前端将 Token 存于 **localStorage**（同域前后台，便于刷新保持登录）；所有管理 API 请求经统一请求头携带（如 `Authorization: Bearer <token>`）。
- 登出 / 改密后，服务端**立即作废**对应 Token。
- 建议：连续操作时可选「滑动续期」（每次请求刷新有效期）——列为建议项，默认固定 2 小时。

### 6.4 初始密码策略

- 系统安装/初始化时**生成随机强密码**（长度 ≥ 12，含大小写字母 + 数字 + 符号），**不使用 admin/123456 等弱口令**。
- **无默认弱密码**：不预置任何已知口令。
- 初始密码标记为「待修改」，**首次登录强制跳转改密页**，未改密前除改密/登出外不可访问任何管理功能。
- 初始密码由初始化脚本输出到终端/写入手册，运营首次登录后即改。

### 6.5 后台路径（可配置）

- 后台入口路径前缀由**环境变量**配置（示例 `CMS_PATH=/manage-x7k2`，前端 `VITE_CMS_PATH`，后端同名配置）。
- **不固定为 `/admin`**，避免被批量扫描。
- **未配置路径时（空/未设置），后台整体返回 404**，绝不能在默认路径暴露后台或登录页。
- 建议前缀包含随机字符段（≥ 6 位），部署时由部署方自定义。
- 路径**同时约束前端路由与后端管理 API 前缀**，两者必须一致（前端跳登录页与后端校验用同一配置）。

### 6.6 其它安全要求

| 项 | 要求 |
| --- | --- |
| 登录接口限流 | 同一 IP 对登录接口的请求频率限制（如 1 分钟 ≤ 10 次），超限返回 429/统一错误码 |
| SQL 注入防护 | 全部使用 ORM/参数绑定，**禁止字符串拼接 SQL**；输入经 Validate 校验 |
| 越权防护 | 所有管理 API（内容 CRUD + 留言 + 改密）必须经**鉴权中间件**；未登录/Token 无效一律拒绝（返回未授权错误码），**不允许**任何管理接口匿名可访问 |
| 越权粒度 | 每个管理员只能通过「修改密码」操作**自身**密码（需校验原密码），**不可改他人密码**；他人密码只能由管理员经「账号管理 → 重置密码」生成一次性随机密码并**强制其下次登录改密**，任何接口均不返回他人密码哈希 |
| XSS 防护 | 后台输入内容在前台渲染时需转义（尤其富文本 P1 引入后必须做白名单过滤） |
| CSRF | 采用 Token 置于请求头（非 Cookie）天然免疫 CSRF；如后续改用 Cookie 需补 CSRF Token |
| 敏感信息 | 错误信息不泄露堆栈/数据库结构；生产关闭 `APP_DEBUG` |
| 留言接口暴露 | 现有 `GET /api/message/list` 必须纳入鉴权（当前为匿名，属安全缺口，本次修复） |
| 传输安全 | 生产环境建议 HTTPS；Token 属敏感凭证，不得出现在 URL/日志 |
| 操作留痕（P1） | 登录、增删改操作写操作日志，便于事后审计 |
| 密码强度 | 新密码长度 ≥ 8 且含字母 + 数字；禁止与账号名相同 |

### 6.7 新增错误码（沿用原 PRD 错误码体系）

| code | 含义 | 说明 |
| --- | --- | --- |
| 0 | 成功 | 沿用 |
| 1001 | 参数校验失败 | 沿用 |
| 1002 | 重复提交 | 沿用 |
| 4004 | 资源不存在 | 沿用（含未配置后台路径时的 404） |
| 5000 | 服务器内部异常 | 沿用 |
| **1003** | 未登录 / Token 无效或过期 | **新增**，前端收到后跳登录页 |
| **1004** | 账号或密码错误 | **新增**（不区分账号/密码，防枚举） |
| **1005** | 登录失败次数过多，账号/IP 已锁定 | **新增**，`message` 含剩余时间 |
| **1006** | 需要先修改初始密码 | **新增**，前端据此跳改密页 |
| **1007** | 原密码错误 | **新增** |
| **1008** | 请求过于频繁（限流） | **新增** |

> 前端统一按 `code` 分流：`1003` → 跳登录；`1006` → 跳改密；其余 → 展示 `message`。

## 八、数据迁移需求

**目标**：把现有 5 个数据文件（约 373 行）的写死内容，在**不丢失、不改变内容**的前提下导入 MySQL，并支持幂等重跑。

| 项 | 要求 |
| --- | --- |
| 触发方式 | 提供**初始化脚本/命令**（如 `php think cms:init` 或 SQL 脚本 + Seeder），部署时执行一次 |
| 迁移内容 | products(8) / news(7) / cases(6) / advantages(4) / about(1) / site_config(1) 全部条数，字段逐个对应（见第七节映射） |
| 幂等性 | 以 `id` 唯一键判断存在则跳过或更新，**可重复执行不产生重复数据** |
| 一致性校验 | 导入后条数与源文件一致（8/7/6/4/1/1）；前台内容与导入前**逐字段一致** |
| 管理员初始化 | 同一脚本创建初始管理员账号 + **随机强初始密码**（首次登录强制改密） |
| 敏感输出 | 初始密码输出到终端并写入手册（或 `.env`），不落库明文；不写入代码仓库 |
| 回滚 | 迁移为新增表，**不修改/不删除** `message` 表既有数据；如失败可清空新表重跑 |
| 建表 | 提供建表脚本（5 张内容表 + `site_config` 单例表 + 管理员/会话/登录失败计数表），utf8mb4 |
| 兼容性 | 迁移前的前端仍能正常构建（数据文件可保留作为 fallback/后备，不做硬删除） |

**说明**：本项只提需求，具体脚本形态与表结构由架构师设计（见待确认 Q3）。

## 九、前台改造范围

**目标**：把「静态 import 数据文件」改为「API 动态读取」，后台改完即生效。

| 页面/组件 | 现状 | 改造后 | 优先级 |
| --- | --- | --- | --- |
| 首页 `Home.tsx` + BusinessSection | 读 `data/products.ts` 前 N | 请求 `/api/product/list`（或首页聚合接口） | P0 |
| 首页 StatsSection | 读 `data/advantages.ts` | 请求 `/api/advantage/list` | P0 |
| 首页 CasesSection | 读 `data/cases.ts` | 请求 `/api/case/list` | P0 |
| 首页 NewsSection | 读 `data/news.ts` 前 3 | 请求 `/api/news/list` | P0 |
| 产品服务 `Products.tsx` | 读 `data/products.ts` | 请求 `/api/product/list` | P0 |
| 产品详情 `ProductDetail.tsx` | 从数组 find | 请求 `/api/product/detail?id=` | P0 |
| 新闻中心 `News.tsx` | 读 `data/news.ts` | 请求 `/api/news/list` | P0 |
| 新闻详情 `NewsDetail.tsx` | 从数组 find | 请求 `/api/news/detail?id=` | P0 |
| 关于我们 `About.tsx` | 读 `data/about.ts` | 请求 `/api/about/detail` | P0 |
| 全站（Navbar/Footer/SEO/公司名） | 读 `config/site.config.ts` 常量 | 请求 `/api/site/config`（`SiteConfigProvider` 注入，静态值为兜底） | P0 |
| `services/api.ts` | 仅 `submitMessage` | 扩展为**统一请求封装**：承载 Token、统一错误码分流、内容读取方法 | P0 |

**前台 API 改造的体验保障要求**：

1. **加载态**：列表/详情请求期间显示骨架屏或 Loading 占位，避免白屏。
2. **错误态**：请求失败显示友好提示 + 「重试」，不出现空白页。
3. **空态**：无数据时显示「暂无内容」占位。
4. **缓存策略（避免首屏变慢）**：
   - 内容类 GET 接口可采用**短时缓存**（如前端内存缓存 / HTTP `Cache-Control` 短 TTL），减少重复请求。
   - 列表接口支持分页参数（首页摘要只取少量）。
   - 首页可考虑**聚合接口**一次返回多区块数据，减少请求数（由架构师决定）。
5. **首屏不退化**：核心内容（Hero/联系方式）优先渲染，内容区块**懒加载 + 骨架屏**。
6. **SEO 兼容**：内容动态化后，详情页 title/description 在数据到达后写入（保持原 PRD P0-10 不退化）。
7. **旧数据文件处置**：可保留 `src/data/*.ts` 作为 fallback（接口失败时降级渲染），或作为迁移脚本的数据源；是否删除由架构师决定。

> 注：本站为 SPA，动态取数后首屏来源从「打包内联」变为「网络请求」，需通过加载态 + 缓存 + 聚合接口把体验损失降到最低，验收标准见第十一节。

## 十、UI 设计方向（后台）

**风格**：**简洁、克制、以内容为中心**。沿用前台设计 token（`tailwind.config.js` 已固化的 colors / fontFamily / borderRadius），后台不引入新的视觉体系，保证品牌一致性。

### 10.1 布局

| 区域 | 说明 |
| --- | --- |
| 左侧边栏（固定宽 ~240px） | Logo/项目名 + 模块导航（产品/新闻/案例/优势/关于我们/留言/修改密码）；当前项高亮（主色底或左侧色条） |
| 顶部条 | 面包屑/页面标题 + 当前账号 + 登出按钮 |
| 内容区 | `bg-bg-soft` 背景 + 白色卡片容器承载表格/表单 |
| 移动端（<768px） | 侧边栏收起为抽屉（汉堡按钮开合），表格转卡片式或横向滚动 |

### 10.2 视觉规范（沿用前台 token）

| 项 | 取值 |
| --- | --- |
| 主色 | `--color-primary #1E4FD8`（导航高亮、主按钮） |
| 文字 | `#1A1A1A` 主 / `#5A6472` 次 / `#8C97A6` 辅助 |
| 边框/分割 | `#E5E8EE` |
| 背景 | 页面 `#F7F8FA`（`bg-bg-soft`），卡片 `#FFFFFF` |
| 圆角 | 卡片 `--radius-md 12px`；按钮 `--radius-btn 8px` |
| 阴影 | `--shadow-sm`（卡片默认）/ `--shadow-md`（hover/弹窗） |
| 间距 | 基数 4px，表单行间距 16–24px |

### 10.3 组件风格

- **按钮**：主按钮实心主色；次按钮描边；**危险操作（删除）用错误红 `#F04438`**；提交中置灰 + Loading。
- **表格**：表头浅灰底、行 hover 高亮、斑马纹可选；操作列固定右侧。
- **表单**：标签在左或上；必填项标 `*`；校验错误红字置于字段下方。
- **反馈**：Toast（成功/失败）；删除/危险操作用确认弹窗二次确认。
- **空态/加载**：统一空状态插图 + 文案；加载用骨架屏/Spin。
- **安全提示**：登录页不区分「账号错/密码错」文案；锁定态明确提示剩余时间。

### 10.4 与前台的关系

- 前后台**同一 SPA 工程**，后台使用**独立布局**（`CmsLayout`）与**独立路由前缀**（`/{CMS_PATH}`），与前台路由互不干扰。
- 后台共用前台已固化的通用组件（Button/Card/Toast 等）与设计 token，避免重复造轮子。

## 十一、验收标准（增量）

| 项 | 标准 |
| --- | --- |
| 登录安全 | 正确密码可登录；错误密码统一提示；连续 5 次失败锁定 10 分钟（账号+IP）；锁定期间正确密码也拒绝 |
| 初始密码 | 系统无默认弱口令；初始密码为随机强密码；首次登录强制改密，改密前无法访问其它管理功能 |
| 会话 | Token 有效期 2 小时；过期后管理 API 拒绝并跳登录页；登出/改密后旧 Token 立即失效 |
| 后台路径 | 可通过环境变量配置；未配置时后台整体 404；不暴露在 `/admin` 等默认路径 |
| 内容 CRUD | 5 类内容均可增删改查（列表 + 搜索 + 分页 + 二次确认删除）；网站配置为单例编辑；字段与 TS 类型一致 |
| 前台生效 | 后台修改内容后，前台**刷新即生效**，无需重新构建 |
| 数据迁移 | 迁移脚本幂等可重跑；导入后条数 8/7/6/4/1/1 且内容与源文件逐字段一致 |
| 留言管理 | 后台可列表/搜索/查看/标记/删除；接口**必须鉴权**，匿名访问被拒 |
| 账号管理 | 可列表/搜索/新建/启用停用/重置密码/删除；新建与重置返回**一次性**随机强密码且仅展示一次；停用/重置/删除后目标账号会话**立即失效**；**不能操作当前登录账号**；**主账号不可停用/删除**（`cms:init` 创建的初始账号 `is_primary=1`，任一时刻全库恰好 1 个）；停用/删除**启用中**账号时**至少保留 1 个启用账号**；重复账号名返回 `1002`；响应**不含**密码哈希 |
| 越权防护 | 任何管理 API 未带有效 Token 一律返回 `1003`；无法匿名读写 |
| 前台体验 | 加载态/错误态/空态齐备；首屏核心内容不白屏；LCP 仍满足原 PRD < 2.5s（或差距可接受） |
| 响应式 | 后台在 375px 无横向溢出、侧边栏可开合、表格可用 |
| 一致性 | 全站响应统一 `{code,message,data}`；错误码按第六节 6.7 执行 |

## 十二、不做什么（明确边界）

为避免范围蔓延，本次**明确不做**以下内容（部分列 P1/P2，本增量 P0 不做）：

1. **不做多租户/SaaS 化**：仍是单站点单企业后台，不支持一个后台管多个网站。
2. **不做角色权限体系（RBAC）**：已支持**多管理员账号**（C-P1-4 ⚑ 已交付），但管理员之间**权限完全相同**，不做角色/权限区分（RBAC 列 P2-2）。
3. **不做工作流/审批流**：内容无「提交-审核-发布」审批链。
4. **P0 不做富文本编辑器**：正文先按纯文本/换行处理（富文本列 P1）。
5. **P0 不做图片上传**：图片仍填路径（上传列 P1）。
6. **P0 不做草稿/定时发布**：保存即生效（草稿列 P1）。
7. **不做国际化**：后台与站点均为简体中文（沿用原 PRD）。
8. **不做前台 UI 大改**：本次前台仅「数据来源」改造，**视觉与页面结构不变**。
9. **不做站点配置（site.config）上云**：公司名/联系方式等仍为配置文件（列 P1-6），本次不动。
10. **不做数据统计/数据看板**：列 P2。
11. **不做第三方集成**：不接入邮件/短信/云存储/SSO/OAuth。
12. **不删除现有数据文件与代码**：采用新增为主、渐进替换，保证可回滚。
13. **不做移动 App / 小程序后台**：仅 Web 后台。
14. **不做数据库迁移工具（如 Laravel Migration）**：用项目自有初始化脚本，不引入额外框架。
